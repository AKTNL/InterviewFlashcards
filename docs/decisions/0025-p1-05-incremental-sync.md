# ADR 0025：持久化增量游标与异步变更通知

- 日期：2026-11-01
- 状态：采用，仓库实现与本地验收完成，尚未发布公网
- 依据：开发文档 P1-05，M5 已签收。当前活跃页每 30 秒检查修订，发生变更时队列前后均取完整快照；答案、草稿、来源和历史共同增长，双设备操作也存在等待刷新问题。

## 决策

1. 通知采用同源异步 HTTP 长轮询，约 20 秒心跳、每秒检查已提交游标。沿用现有登录身份和请求取消机制，不增加消息队列、Redis 或 WebSocket 服务。通知丢失不会丢失数据，客户端始终使用最后成功应用的游标补拉。
2. V19 在业务表增加延迟触发器，等业务、收据及用户修订写入完成后，记录同一事务内的行标识；独立修订标记用来验证连续覆盖。包括后台解析和删除，不要求每个业务回调人工列举变更行；触发器不改变既有修订数量。
3. 日志只存行键，增量返回当前最终行或删除标记。复合关联、按日期重练额度及无 id 的参数历史明确使用实际主键。REPEATABLE READ 与共享用户锁将头信息、覆盖检查、内容读取保持一致。
4. 历史保留 7 天，单次最多跨 1000 个修订、5000 个不同键；初次连接、过期、空档、代次改变或超限回退到全量。恢复个人 ZIP 不恢复传输历史，不降低修订或复用旧代次。
5. 客户端原子发布合并状态和游标，保留编辑表单、旧版本和幂等队列。队列预检和写后读取共用增量加载；没有尝试写入时取消第二次重复读取。相关页面可按变更表筛选刷新，跨日、跨代次和全量始终兜底。
6. 隐藏/离线停止客户端通知等待，激活/重连从旧游标补拉。通知失效保留 30 秒修订轮询和手动强制全量刷新，不能把通知连接状态当作待写入内容已确认。

## 代价与边界

单进程通知等待上限 512、每账号 8；定时数据库检查适用于当前个人/朋友规模。首次完整快照、巨大单行内容和分页之外的内存占用仍有成本；本任务改善后续变化传输，不宣称解决任意规模数据。新增同步表时必须扩展全量白名单、触发器主键及消费者依赖；新增业务写入仍需推进用户修订。
